# FAST SHM completion candidate — physical gain unproven

This private libGL uses the exact qualified Y composition, replacing only `glx_lab_frontend.o` and `remesa_fast_shm.o`. The separate X11 pipeline optimization is not included. Keep the qualified R bootstrap and root's physically approved kernel/assets. Default remains PUTIMAGE; activation requires `REMESA_GEARS_PROFILE=FAST` and `REMESA_GEARS_PRESENT=SHM`. No SSH, X server or GPU operations were performed by this agent.

The old helper requested no completion event and allowed reuse after `request_check` alone. This candidate requests completion and requires both checked PutImage success and a matching event before acknowledging or rewriting the single 4,096,000-byte buffer. It adds no GPU commands, readbacks, hashes, checkpoints or diagnostic logs.

The frontend already holds the lab mutex and Display lock, flushes Xlib, and borrows its XCB connection. First SHM presentation binds that live Display and timeout once. Xlib keeps event ownership. A pure `XCheckIfEvent` predicate matches Display, event type, drawable, private segment, offset and opcodes; synthetic events and older serials are rejected. Serial comparison handles 32-bit wrap and allows later sequence progress, since the event describes the last request processed. One private request in flight prevents ambiguity. Arrow, Expose and other unmatched events remain queued.

The helper checks the queue before polling the connection, because the checked request may already have buffered completion. The new completion wait has a monotonic deadline and handles EINTR and connection failure. This does **not** globally bound existing checked XCB calls, queries or GC operations.

Lock order remains lab mutex → Display lock → helper mutex. SHM close uses the same order while the Display is still alive. On uncertain completion or any PutImage-attempt error, the helper becomes poisoned: future calls reject before copying or dereferencing the Display. Normal close returns EBUSY without detach, unmap or FD close. At most one 4 MB segment remains retained until process teardown; there is no production reset or late-completion recovery. Successful completed close preserves checked detach → unmap → FD close. Initialization failures before PutImage can clean up normally. No frame is resubmitted as fallback.

The existing `-lXext` flag previously disappeared under `--as-needed`. Moving the new helper object before the existing X libraries retains it, adding explicit `DT_NEEDED: libXext.so.6`. Root must verify that Mini's loader resolves this existing library **before GPU testing**. Other dynamic dependencies and the qualified X PutImage publisher object are unchanged. No packages were installed.

Actual helper tests passed native, UBSan and i386/qemu: 120 single-buffer frames, complete pixel copy, unrelated event preservation, ten mismatched completion cases, queued-before-poll completion, wrap, multiple polls/EINTR, timeout, late completion, disconnect, checked error, zero cookie, clock/poll/FD errors, resize, poison retention, dead Display avoidance and normal/in-flight close. File, mmap, clock, Xlib and XCB APIs are mocked. Fixture resets simulate process teardown, not production recovery. Initial missing-header and link-order failures are preserved.

After geometry passes physically, root should verify the loader, MIT-SHM FD support, actual completion conversion, correct 1280×800 output, arrow delivery and clean retirement/close on the Mini. Compare at least 600 original GLXGears frames against exact Y/R using the same approved kernel/assets. Keep PUTIMAGE unless physical FPS and stability improve; no gain is claimed here.
