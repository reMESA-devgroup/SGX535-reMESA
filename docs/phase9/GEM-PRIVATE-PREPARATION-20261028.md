# Retained GEM jobs now supply private MMU bindings

The private MMU preparation code is now connected to the retained GEM service
through `remesa_gem_private_prepare/release`. The bridge derives every VA,
page array and size from the job's held backing. A trusted caller supplies
only exact job IDs and access/cache policies. It cannot inject extra PFNs,
addresses or resources. This is an unbound-directory preparation loan, not an
executable job, root publication, IRQ reservation or runtime admission.

## Lifetime and memory contract

The existing qualified GEM service already acquires `gma_power_begin(dev,false)`
and the frozen-owner exclusion at session open, releasing both only after safe
close. The new loan uses that session lifetime and the existing job attachment
slot, preventing cancellation and endpoint close while its private owner lives.
This does not establish complete device/MMU-writer exclusion. The caller must
still meet the private-owner trusted-call contract before preparation.

Preparation authenticates the exact ticket, prepared/nonquarantined state,
complete job-ID list, retained object generations, holds, pinning, mappings,
page counts, CPU lease exclusion and initialized readable inputs. It checks the
actual cached-RW default mapping, then VA-sorts a local allowlist without
changing job order. Access/cache policies remain paired with their pages.
The existing private builder copies that allowlist, retains pages and audits
the unbound tree with the narrowed PTE permissions.

The loan attaches before private preparation can return a retained exceptional
owner. Ordinary allocation failures with no owner roll back the attachment,
leaving the prepared job and original holds unchanged. An exceptional retained
owner or impossible success-without-owner quarantines the job; no retirement
or cleanup is fabricated. A reserved executor rejects all attempts to use the
legacy issue route with this preparation-only object.

Release first calls private-owner release. A bound/uncertain owner refuses
release, preserving the attachment and GEM holds. Only a successful unbound
release detaches the loan; the original job stays prepared with its original
holds until explicit cancellation or a separately qualified executor takes it.
There is no data readback, hash, buffer clearing, CPU mapping, cache flush,
submission, fence or completion generated by this bridge.

## Qualification and staging

Native, UBSan and i386 each pass309 bridge checks. These execute the retained
GEM service source against modeled kernel/GEM primitives and MMU callbacks;
they are not real Linux GEM allocations or hardware tests. Cases include
1280x800,640x640,641x479 backing sizes, unsorted VAs, preserved policy/page
pairing, stale ticket/IDs/counts/policies, uninitialized reads, mapping failure,
allocation failure, retained exceptional owners, blocked release and rejection
of legacy issue. Quarantined cases exit separate CPU child processes with
retained model state; no fake GPU retirement is performed. The actual private
owner/auditor has its separate previously retained qualification.

`stage_twod_reservation.py --with-private-mmu-preparation` optionally stages the
bridge and private MMU components in fresh sources. No new ioctl, runtime knob,
executor registration or automatic root binding is added. Both original antiX
translation units `mmu.c` and `remesa_gem_memory.c` compile without warnings;
symbol records bind the GEM bridge's MMU references to the actual owner API.
This is not a full module link or installation.

`v2/LEGACY_STAGING_COMPARISON.json` checks all five existing generated source
profiles against commit3adab1c: all are byte-identical when the new option is
false. Staging changes are explicit; qualified checkpoint files and all31
protected files remain unchanged. v1 initial295-check and v2/v3 runs are
preserved; v2 adds initialization/mapping failures and v3 replaces padded
struct comparison with explicit empty-token fields. No Mini12 operation or
new FPS measurement occurred.

## Remaining executor work

This closes the GEM-to-private-page-list preparation gap. Publishing the root
still requires whole-interval exclusion of console/native/fixed producers,
MMU writers, power transitions and IRQ ownership, followed by authenticated
completion/visibility/retirement and checked restoration before releasing the
loan. The session's frozen-owner claim alone does not block every writer.
Actual texture/shader/resource closure must include every indirect dependency;
this API cannot infer it from an arbitrary command buffer. General GL/GLES2,
desktop integration, physical isolation and installability remain unfinished.
PDS encoding research is not the default focus unless physical evidence points
to a PDS fault.
