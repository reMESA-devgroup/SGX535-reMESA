# X11 + Gallium integration — PARTIAL
X11_READBACK_PRESENT_PASS is demonstrated on the actual Mini12: one owned32x32 window, depth24 TrueColor/BGRX, stride128, authenticated previous OpenGL physical readback, explicit bottom-left to top-left conversion, checked server acknowledgement and GetImage RGB24 equality. Source136green/888black, zero channel differences, window destroyed, exit0. The unused fourth X byte is excluded from RGB equality; both full server and normalized RGB hashes are recorded. See x11-actual/RUN.json, report.json and X11_VERIFIED.json. Boot identity and executable/input hashes are retained. No GL context or new SGX shader submission occurred. The executable used is the sealed prior-checkpoint probe, not the new attachment/swap implementation.

New Gallium attachment API in remesa_screen.c owns independent front/back resources through the existing resource allocator/reference system. Replacement allocates all new attachments before releasing old references; a second-allocation failure rolls back tentative backing. Readers retain old resources. Generation increments only on successful replacement; depth and larger render attachments explicitly return ENOTSUP. No implicit preservation, rendering or capability increase is introduced.

remesa_xcb_present_drawable joins that attachment state with existing resource writer-fence/readback ownership and checked XCB publication. It requires exact drawable geometry, supports explicit row origin, and exchanges front/back references only after all image/GC acknowledgements succeed. EAGAIN, connection/image/cleanup failure and counter overflow cannot commit a swap. Tests exercise4 mock frame publications, uncertain-cleanup rejection, reader lifetime, failed replacement, invalid resize/depth and old-resource ownership. These are CPU tests, not physical repeated frames or glXSwapBuffers.

GLX_DRI_CONTEXT_PASS is NOT achieved. The real DRI screen factory still rejects at OPENGL_ADMISSION; current build GLX remains disabled. There is no GLX drawable/state-tracker attachment binding, handle import/export, real swap callback or resize/event hookup. The new APIs are reusable pieces for that frontend, not a replacement for it. The actual installed glxgears audit from the parent checkpoint remains valid: default doublebuffer/depth visual, fixed-function matrices/normals/materials/lighting/culling, quads/quad strips (Mesa may triangulate), clear and repeated swaps. Position-copy VS, constant FS and one replace-only32x32 job cannot satisfy those requirements.

The next implementation dependency is physical target/preservation state plus frontend attachment binding. General GLX admission must not be opened while the advertised states cannot be executed. No glxgears process, physical frame, continuous animation,1280x800 rendering or FPS was measured this round; no software renderer was used as evidence.
