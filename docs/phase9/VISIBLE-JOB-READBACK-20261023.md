# Held-job framebuffer readback

IMPLEMENTED_OFFLINE: `remesa_gem_job_copy_visible` is a kernel-only bounded copy from a held GEM job. It accepts an exact ticket and held object ID, rejects non-visible states and out-of-range chunks, verifies all job mappings, and copies at most 4096 bytes. The existing job CPU view is reused; otherwise a temporary virtual mapping is released after the copy. No command submission, ioctl, executor registration, cache operation or state transition is introduced. Kernel callers must provide output disjoint from service/GEM storage.

Resource lifetime: VISIBLE requires the existing executor publication callback and page synchronization. ACKNOWLEDGED is also accepted while job holds remain. Normal memory leases remain denied during the held job. PTE corruption quarantines the job and retains resources; temporary map allocation failure leaves state/holds intact and copies no output. Retirement invalidates the ticket. The routine does not authenticate an injected executor or turn CPU tests into physical evidence.

New source relationship: the ordinary memory READ API already supports arbitrarily many bounded chunks, but rejects every action on held resources (native service `act`: `if(b->holds) return -EBUSY`). The fixed native owner capture additionally requires exactly one page. The new kernel routine supplies the missing retained-lifetime copy primitive without weakening either restriction. A 1280×800 BGRA8 frame requires exactly 1000 chunks. A new userspace/observer capture protocol is still needed for a physical claim; this helper alone does not replace it.

Validation: unchanged original native GEM service source was compiled with injected kernel APIs plus this new fragment. Four controls cover complete1000-page data, publication failure, last-page PTE corruption and temporary-map allocation failure. State, ticket/object membership, extent, cross-page reads, access after acknowledgement and rejection after retirement are also checked. All run native, UBSan and i386/QEMU. The same fragment was appended to an isolated copy of the original native source and compiled with its actual antiX kernel object command. No resulting object/module was loaded.

Integration: the fragment and declaration are in the worktree under kernel/remesa/gma500. The isolated kernel-source integration appends one include to remesa_gem_memory.c; old native sources, runtime modules, ADMISSION and28 gate files remain unchanged. The new helper is deliberately not exposed through the active fixed profile.

Remaining: define the complete new depth/1280 native scene image/resource-use profile, then bind a bounded capture caller to actual completion/publication/retirement and the observer. This requires owned scene/DPM/control/event/background resources and the correct1280 scene-cookie routing. Repeated physical execution, variable shader transforms/varyings and original glxgears client integration remain incomplete. GPU submissions this increment:0.
