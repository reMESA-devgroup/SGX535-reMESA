# Real OpenGL client for the first general warm transaction

The existing native OpenGL client now accepts `--session-2` in addition to its
unchanged `--execute` and `--prepare-only` modes. It uses real Mesa fixed
function APIs, `glClear`, `glDrawArrays`, flush and `glReadPixels`, then the
[new bounded kernel/C transport](general-session-transport.md).

This experiment contains **one API draw replayed as two GPU jobs**, first cold
and then warm. It does not claim two application frames, sustained animation,
FPS, general GL2.1 or GLES2 support. The context still reports computed GL1.3.
No vertices, shaders, raster output or reference image are generated by a CPU
renderer as a substitute for SGX execution.

The collector checks the existing packet/placement and creates its four guards
before opening the session. It records OPEN and each SUBMIT request/response
separately. After each acknowledged job, it queries the complete18-binding LAB
trace and checks receipt, IDs, addresses, limits and planned action counts.
It captures COLOR, Z, READ inputs, remaining CPU/source owners and guards in
`session-000001/` and `session-000002/`, without overwriting the first job.
It does not read either32MiB DPM pool. These reads are qualification work in the
collector, outside production FAST.

The collector closes the general source/backing session only after both valid
receipts and captures. It then acknowledges the frontend's single API draw.
Ordinary frontend resource teardown and `glReadPixels` follow. An uncertain
OPEN, SUBMIT, trace or CLOSE returns ambiguous issuance, retains the frontend
owners and does not retry, close again or free the buffers.

## Archive verification and supervision

`tools/remesa/verify_general_session_capture.py` checks both complete176-byte
exchanges, monotonic operations, SGX535 rev121/PDS identity, phase9/ledger7,
closed ownership, all13 READ inputs, CPU/source backing and four guards.
Each job's full action/USE plan must equal the pinned previous physically
qualified plan. Its66 control words must also equal the independently exported
kernel-validator oracle. Attributable source completion samples must match the
previously accepted separate or combined status patterns for that operation.

It compares all COLOR pixels and defined Z24 bits against the existing pinned
oracles at1280×800 or640×640, and checks the final actual `glReadPixels` bytes
against the established bottom-up copy contract. Undefined Z X8 remains ignored.
It never marks an archive as physical proof: boot/module identity, source
lineage, gates, kernel health and stock recovery require the outer audit.

`tools/remesa/general_session_native.py` is the corresponding supervisor. Its
default mode writes a plan and opens no device. The execution mode passes one
borrowed FD to the real client, verifies the returned archive and checks the
six remaining objects, complete actual owner graph and enclosing guard VAs.
Only after acknowledged session close and valid evidence does it explicitly
unmap/unpin/destroy those objects and close the memory context. An uncertain
client result, invalid evidence or failed cleanup suppresses further cleanup
requests. Closing the OS FD delegates retained-state handling to the existing
driver loss protocol; it is not a recovery or GPU retirement claim.

Both tools accept `--asset-root` so the original pinned catalogue can be used
with relocated payload files without rewriting its metadata. They do not enable
controls, install, reboot, retry submissions or present anything onscreen.
