# Native vertex-color clamp integration

The fixed-function OpenGL frontend requests `clamp_vertex_color`. The existing
gears lighting program computes material/light COLOR0 and preserves scene
alpha, but its diffuse `max(dot, 0)` does not clamp the final color. Ignoring
the raster flag would therefore lose application semantics.

The driver now has an owned effective shader variant for that request. It
keeps the original canonical NIR-derived program unchanged and represents the
additional operation as a distinct complete host semantic profile. Linkage
revalidation and the selected resource identity distinguish the two programs.
The ordinary selected-resource and scalar shader launch restrictions remain.

## Code and storage

The variant reuses the existing gears body, component-control, max, min and
tail encoders. Its three-instruction suffix is identical to bytes 32–55 of all
five original compiler outputs in
`/home/gama/sgx535-offline/lambert-vs-minimal-20261023T221500Z/white-oracles.txt`.
It clamps four COLOR0 lanes in numeric output class1/base4 and needs no extra
temporary or uniform. This composition does not requalify physical execution.

| Program | Effective CODE | Reserved USE extent | Following FS offset |
| --- | ---: | ---: | ---: |
| Existing lighting | 320 bytes | 320 bytes | 320 bytes |
| Lighting plus COLOR0 clamp | 344 bytes | 352 bytes | 352 bytes |

The original 312-byte lighting body and 8-byte typed tail remain byte-exact.
The variant inserts 24 bytes of actual clamp instructions before that tail.
The eight bytes after CODE344 are zero storage padding, never instructions.
P/N inputs, parameter source37/transfer40, eleven temporary words and eight
output words remain unchanged.

The new internal PDS producer profile is
`REMESA_PDS_SELECTED_VS_GEARS_ATTRIBUTE_CLAMPED_PADDED3`. It retains the existing
vertex PDS producer while checking its distinct committed/reserved USE sizes.
The legacy state14 constructor refuses this profile; the explicit homogeneous
state15 owner can prepare it. An internal PDS profile number is not a kernel
test profile selector.

The separate [kernel body/state validation](kernel-clamped-gears-admission.md)
now recognizes CODE344 only with an authenticated state15 draw. Separately,
the [actual-API LAB catalogue](clamped-api-lab-catalogue.md) registers exact
input candidates as wire selectors5/6. Neither change establishes physical
qualification or removes the pending raster guard.

## Raster descriptors and execution

The explicit homogeneous frontend can retain a supported OpenGL raster
descriptor and use its clamp request in the effective shader snapshot. These
descriptors are marked pending. The normal draw guard refuses that class
before scene allocation or dispatch, including a half-center descriptor with
the other guard bits zero. The separate [finite API raster
contract](homogeneous-api-raster.md) admits only the explicitly enabled sealed
W2 recipe; retaining a descriptor alone never establishes draw admission or
general sampling, edge, clipping and culling support.

The old GLXGears runtime, default screens, previously qualified CODE320 and
physical OpenGL/GLX tests are preserved. The new frontend still does not claim
full OpenGL 2.1 or GLES 2.0 conformance.

## Input storage and lease ownership

Actual Mesa execution exposed an unrelated mapped 512KiB vertex buffer: Mesa
keeps its immediate-mode scratch buffer mapped even when `glDrawArrays` uses
other inputs. The existing device-wide native preparation guard correctly
refused the live GEM lease. Releasing only the driver's upload managers does
not close this Mesa-owned map. The failed admission traces retain the exact
handle, size, bind and map flags; no foreign lease was forcibly released.

The explicit native frontend now gives PIPE_BUFFER inputs owned host storage.
Its existing scene preparation copies raw vertices, indices and coefficients
into immutable GEM owners. Vertex transformations, normalization, lighting and
fragment rendering remain GPU programs; no transformed vertices or pixels are
generated by the host-storage path. COLOR and Z attachments stay GEM-backed.
The existing provider-wide GPU map guard and kernel gates remain intact.

Host allocations are zero-initialized and have an atomic screen-wide byte
budget derived from `max_resource_bytes` (64MiB when unspecified). Transfers
retain their existing bounds, map exclusion, explicit-flush and content-epoch
rules. Pending host/staging views are protected against metadata-output
aliases before the driver's own upload maps can be released. Raw input-buffer
copies also work when the separate native 2D copy callback is configured.

An additional transport bug was confirmed: unmapping a WRITE lease must use
the original WRITE mode even when no explicit-flush range became dirty.
Dirty state updates content epochs; it does not change lease ownership. The
driver now preserves that mode, and the modeled provider checks it strictly.
The clear-queue suite includes an unflushed WRITE mapping as a regression.

Evidence and failed diagnostics are retained under
`/home/gama/sgx535-offline/vertex-clamp-integration-20261102/v1`.
They distinguish compiler-oracle matching, actual Mesa API inputs, modeled
resource construction and physical execution. This component has no new GPU
submission or physical approval.
